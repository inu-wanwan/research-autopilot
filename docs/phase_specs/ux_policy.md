# 人の操作と通知の UX 方針（全 Phase 共通）

2026-10-12 ユーザー決定。Phase 5 / 6 / 9 / 10 の承認・通知・再開の操作はすべてこの方針にそろえる。
背景：INU-292 / INU-305 の E2E で、人がどこで何をすれば再開するのかが分からない状態（行き止まり）が繰り返し起きた。

## 1. 原則

1. **行き止まりを作らない**：人の操作が必要な状態では、必ず「何が起きたか・なぜか・何をすれば再開するか」とその操作手段（ボタンまたはリンク）がそろったメッセージを 1 通出す。
2. **人の操作は approvals に集める**：承認・差し戻し・再開・入力待ち・打ち切りなど、人の判断や操作が必要なものはすべて approvals チャンネルに送る。他のチャンネルは見るだけ。
3. **役割分担**：Notion は仕様の編集と実行開始（Run Autopilot。タスク作成 → 確認 → 実行の流れのため残す）。Discord は判断と制御（承認・差し戻し・停止・再開・打ち切り）。
4. **古いボタンを放置しない**：版が上がった・失効したメッセージはボタンを無効にし、「v2 に置き換わりました」などと新しいメッセージへの案内に編集する。
5. **再開までの手順を書く**：人の操作が必要なメッセージには、実行が再開するところまでの手順を番号付きで書く（どの Notion の節のどこを直すか、何を押すか、何を待つか、例）。理由ごとに手順の型を持つ。
6. **メッセージの最低限の中身**：状態、理由、次の手順、Notion のリンク、費用・予算の使用状況。

## 2. チャンネルの役割

| チャンネル | 中身 | ボタン |
|---|---|---|
| approvals | 人の判断・操作が必要なものすべて | あり |
| results | サイクルの評価結果・完了報告（Notes の URL 付き） | 実行中の研究には Stop のみ |
| errors | システムの失敗の詳細（調査用） | なし。人の操作が必要なら approvals にも出す |
| logs | 進捗（実装・テスト・計算など） | なし |

## 3. 状態ごとの UX（研究タスク）

| 状態 | 送り先 | ボタン | 人の操作 |
|---|---|---|---|
| 研究計画の承認待ち | approvals | Approve / Request revision / Reject | 計画ページを見て判断 |
| 計画が要入力（needs_input / invalid） | approvals | Resume / Cancel | 書かれた手順どおり Notion の仕様を直す（保存すると自動で再計画。届かない場合のみ Resume） |
| 仕様の編集で承認依頼が失効 | 元のメッセージを編集 | 無効化＋新版への案内 | なし（新版が自動で届く） |
| 実行中 | logs（進捗）、results（サイクル評価） | Stop | 必要なら止める |
| 一時停止（Stop 後） | approvals | Resume / Cancel | 再開または打ち切り |
| 停止（評価で stop・失敗・予算超過） | approvals | Resume / Cancel | 手順に従い必要なら仕様・予算を直して Resume |
| スコープ変更の提案 | approvals | Approve / Request revision / Reject | 判断 |
| 完了 | results | なし | Notes を確認 |
| 子タスク（Phase 2〜4）の失敗 | logs | なし | なし（研究側が再試行・評価し、止まれば「停止」になる） |

Phase 5 / 6 / 9 の承認（onboarding、提案、予算、DAG、外部コード・ライセンス、完了レビュー）も同じ原則で、approvals に手順付きで出す。

## 4. 仕様の編集

仕様（Notion）を編集したら、Autopilot が検知して自動で計画を作り直し、承認依頼を再送する。needs_input で止まっている場合も同じ（人が Resume を押す必要はない。Resume は自動検知が届かないときの予備）。

## 5. 打ち切り（Cancel）

approvals のメッセージに Cancel ボタンを置く（確認付き、承認者のみ）。押すと、研究タスクと未完了の子タスクの Autopilot 実行を止め、Linear をまとめて Canceled にし、理由と操作者を記録する。

## 6. 人の作業（正常時）

タスク作成 → Run Autopilot → 研究スコープの承認、の 3 回。以後は完了まで自律的に進む。人に回すのは仕様・予算・科学的判断が必要な場合だけにし、仕組みの一時的な失敗は自動の再試行で吸収する。人の承認ゲート（研究スコープ、スコープ変更・予算増額、外部コードの初回実行、自動判定できない完了）は減らさない。
