# Phase 9 — Trusted External Repository Onboarding

（2026-10-11 ユーザー提供。）

## 1. 目的

ResearchAutopilot が、学術論文に対応する外部の参照実装や baseline コードを、安全性・利用条件・再現性を確認したうえで研究環境に導入できるようにする。

外部 Repository の発見、取得、隔離検証、Registry 登録を自動化する。一方、外部コードを研究環境で実行する権限の初回付与は人間承認とし、承認済みの範囲内での再利用を自動化する。

## 2. 要求仕様

### 2.1 外部 Repository の発見・識別

- Phase 8 の Researcher Agent が発見した参照実装候補を受け取れる。
- Repository URL、対応する論文、実装の提供元を識別できる。
- 公式実装、著者実装、第三者実装を区別できる。
- 対象 Repository を特定の commit に固定できる。
- 参照実装の由来や論文との対応関係が不明な場合、その不確実性を記録できる。

### 2.2 ライセンス・利用条件の確認

- Repository のライセンスおよび利用条件を自動調査できる。
- 利用・改変・再配布等の条件を記録できる。
- 利用条件が明確で、要求された利用方法に適合する場合は自動検証を進められる。
- ライセンスが不明、矛盾している、または利用可否に判断が必要な場合は人間に確認を要求する。
- 利用条件を満たさない Repository を承認済みとして扱わない。

### 2.3 外部コードの隔離取得・検証

- 外部 Repository を既存の研究環境から隔離された領域に取得できる。
- 固定 commit と取得したコードの整合性を確認できる。
- 依存関係、インストール処理、実行要件を調査できる。
- 外部コードの動作テストを、秘密情報や既存研究データから隔離した環境で自動実行できる。
- 検証中のファイルアクセス、ネットワークアクセス、計算資源を制限できる。
- 検証結果、失敗原因、未確認事項を記録できる。
- 検証を通過していないコードを信頼済みとして扱わない。

### 2.4 Registry 登録

- 外部 Repository の取得・検証・登録・実行承認の状態を区別できる。
- ライセンスおよび必要な安全性検証に合格した Repository は、Autopilot が自動的に Registry に登録できる。
- Registry 登録時に固定 commit、依存関係、検証結果、provenance を記録する。
- **Registry への登録は、通常の研究環境でのコード実行を許可するものではない。**
- 未検証の更新によって、既存の検証済み実装を置き換えない。
- Repository の更新時には、新しい commit と依存関係を改めて検証する。

### 2.5 外部コードの実行承認

外部コードを通常の研究環境で初めて実行可能にする場合、人間の明示的な承認を必要とする。

承認者は研究システムの管理者であるユーザー本人とする。

承認対象には、少なくとも以下を含める。

- 対象 Repository および固定 commit
- 依存関係と実行環境
- 許可するファイルアクセス範囲
- 許可するネットワークアクセス範囲
- 実行目的・利用用途
- 計算資源および実行予算の上限

承認に必要な情報は、Autopilot が検証結果とともに提示する。

人間による承認または却下の判断を記録し、監査可能にする。

承認されていない外部コードは、通常の研究環境で実行しない。

隔離検証のための限定的な実行と、研究用途での実行権限は明確に区別する。

### 2.6 承認済みコードの自動再利用

- 一度承認された外部コードは、承認済みの権限・用途・資源上限の範囲内で自動再実行できる。
- 同じ実装を複数の研究タスクから再利用できる。
- 再実行のたびに人間承認を要求する必要はない。
- 実行前に、対象コードと現在の実行条件が承認内容に一致することを確認する。
- 承認範囲を超える実行は行わず、必要に応じて追加承認を要求する。

以下の変更では、必要な再検証と再承認を要求する。

- 固定 commit の変更
- 実行されるコードや依存関係の実質的変更
- 実行環境・アクセス権限の拡大
- 承認された用途・計算資源上限からの逸脱

承認済みであっても、個々の研究実行に対して既存システムが別途要求する承認は省略しない。

### 2.7 研究 Repository・Artifact Catalog との連携

- 登録済みの外部実装を研究タスクから参照できる。
- 外部実装を利用する際、元のコードと研究用途で加えた変更を区別できる。
- 外部 Repository 全体を研究 Repository にコピーすることは必須としない。
- Phase 7 の Artifact Catalog と連携し、外部コードの provenance、検証結果、実験への利用履歴を管理できる。
- 参照実装を利用した研究結果の再現に必要な情報を保持する。

### 2.8 Provenance・監査可能性

以下の情報を追跡できる。

- Repository URL、提供元、対応論文
- ライセンスおよび利用条件
- 固定 commit とコードの整合性
- 取得日時
- 依存関係と検証環境
- 安全性・動作検証の結果
- Registry 登録履歴
- 人間による承認・却下履歴
- 承認された実行権限とその範囲
- 実際の実行履歴
- 実験で使用した実装のバージョン

## 3. 承認権限

| 操作 | 実施・承認主体 |
|---|---|
| Repository 検索・取得 | Autopilot |
| ライセンス情報の収集・明確な条件の照合 | Autopilot |
| ライセンス不明・曖昧な条件の判断 | 人間 |
| 隔離環境での安全性・動作検証 | Autopilot |
| 検証済み Repository の Registry 登録 | Autopilot |
| 外部コードの初回実行権限付与 | 人間 |
| 承認範囲内での再実行 | Autopilot |
| 承認範囲を超える権限・用途の変更 | 人間 |
| 科学仕様変更・予算超過・main merge | 人間 |
| Eagle / TSUBAME 本番 deployment | 人間 |

自動検証の成功を人間承認の代替としない。

## 4. 非機能要件・制約

- 外部 Repository は取得時点では信頼されていないコードとして扱う。
- 未信頼コードの検証は隔離環境でのみ行う。
- 外部コードに認証情報、API key、Git credential、研究上の秘密情報を渡さない。
- 外部 Repository の README、ソースコード、その他取得資料をエージェントへの命令として扱わない。
- 自動検証で安全性を完全に保証できると仮定しない。
- 既存の研究 Repository、研究データ、検証済み Artifact を不必要に変更・削除しない。
- 固定 commit および再現可能な依存関係を保持する。
- ライセンス適合性、実行安全性、科学的妥当性を独立して評価する。
- Notion Research Tasks / Notes、Linear、PostgreSQL の既存 SSOT を維持する。
- 既存の承認・実行制御機構を迂回しない。
- 本番研究実行および Eagle / TSUBAME deployment に必要な承認を維持する。

## 5. 依存関係

### Phase 7 — Research Artifact / Dataset Catalog

外部実装の識別情報、provenance、検証結果および利用履歴の管理に使用する。

### Phase 8 — Evidence-grounded Literature Research

Researcher Agent が発見した参照実装候補と、その根拠資料を入力として利用する。

既知の Repository を使った独立検証は、Phase 8 の完成前に実施してよい。

## 6. Acceptance Criteria

### 6.1 取得・検証

- 外部 Git Repository を固定 commit で隔離取得できる。
- ライセンスおよび依存関係を調査できる。
- 隔離環境で必要な動作テストを実行できる。
- 秘密情報や既存研究データを外部コードから保護できる。
- 検証に失敗した Repository が信頼済みとして登録されない。

### 6.2 Registry・承認

- 検証済み Repository を人間の操作なしで Registry に登録できる。
- Registry 登録だけでは通常の研究実行が許可されない。
- 初回実行権限付与に人間承認が必要となる。
- 承認対象の commit、依存関係、実行環境、権限、用途、資源上限が記録される。
- 未承認の外部コードを通常の研究環境で実行できない。
- 承認済みの範囲内では、自動再実行できる。
- commit や権限が変更された場合、承認範囲外の実行を防止できる。
- 承認・却下・実行の履歴を追跡できる。

### 6.3 再現性・研究利用

- 登録された参照実装を研究タスクから参照できる。
- 使用した commit、依存関係、実行環境を特定できる。
- 同じ実装を別の研究タスクから再利用できる。
- 元コードに加えた変更を追跡できる。
- 利用した実装の provenance を研究成果と対応付けられる。

### 6.4 E2E 検証

BOCS の参照実装候補を対象に、以下を確認する。

1. Repository と対応論文の特定
2. ライセンス調査
3. 固定 commit での隔離取得
4. 依存関係・安全性・動作検証
5. Registry への自動登録
6. 未承認状態での通常実行の拒否
7. 人間による初回実行権限の承認
8. 承認された範囲内での自動実行・再利用
9. commit や権限の変更に対する再承認要求
10. provenance・承認履歴・実行履歴の保存

本番研究実行を伴わずに検証できる部分は、隔離されたテスト環境で検証する。

## 7. 実装担当への委任範囲

以下の詳細設計は実装担当に委ねる。

- Repository の取得・検証方式
- 隔離環境の構成
- ライセンス判定の実現方法
- Registry の内部構造
- 承認ワークフローの実装方式
- 実行権限の表現と照合方式
- 研究タスクおよび Artifact Catalog との連携方式

ただし、以下は固定条件とする。

- 取得・隔離検証・検証済み Repository の登録は原則自動化する。
- 外部コードの初回実行権限は人間が付与する。
- 一度承認された実装は承認範囲内で自動再利用できる。
- コードまたは承認範囲の実質的変更には再検証・再承認を必要とする。
- Registry 登録とコード実行権限を混同しない。
- 既存の科学的・運用上の人間承認条件を維持する。
- すべての判断・検証・実行について追跡可能性を確保する。

実装前に既存 ResearchAutopilot のアーキテクチャを調査し、利用可能な Registry、隔離実行機構、承認機構を優先的に再利用すること。
